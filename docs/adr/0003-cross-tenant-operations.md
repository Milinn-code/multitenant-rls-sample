# ADR-0003: テナントをまたぐ操作は、操作ごとの SECURITY DEFINER 関数と監査ログに限定する

**Date**: 2026-09-25
**Status**: accepted
**Deciders**: リポジトリ作成者

## Context

運営者による全テナントの集計など、テナントをまたぐ操作はどうしても必要になる。
しかし「RLS を一時的に外す汎用の仕組み」を作ると、それ自体が最大の抜け穴になる。
誰が・いつ・何のためにテナントをまたいだかを、後から確実にたどれることも求められる。

## Decision

テナントをまたぐ操作は、**1つの決まった操作ごとに1つの `SECURITY DEFINER` 関数**として実装する（例: `app.ops_reservation_summary(reason)`）。

- 関数の所有者は `BYPASSRLS` を持つ `cross_tenant_definer`（ログイン不可）。権限は関数が使う SELECT と監査ログへの INSERT だけ
- `SET search_path = pg_catalog, pg_temp` で固定し、関数内の名前はすべてスキーマ修飾する
- EXECUTE は PUBLIC から取り消し、`ops_user` にだけ付与する
- 実行理由（`reason`）を必須にし、結果を返す前に監査ログへ1行書く。呼び出し元は `session_user` で記録する
- 監査ログの INSERT と結果の返却は同じトランザクションなので、監査ログが書けなければ結果も返らない

## Alternatives Considered

### Alternative 1: 汎用の「RLS をすり抜ける」関数やロールをアプリに持たせる
- **Pros**: 新しい横断処理を追加するたびに関数を作らなくてよい
- **Cons**: 任意のクエリが全テナントに対して実行できる。何が実行されたかを監査しにくい
- **Why not**: 攻撃者やバグにとって最も価値のある入口を、自分で作ることになる

### Alternative 2: 横断処理は管理用接続（スーパーユーザー）で直接 SQL を実行する
- **Pros**: 追加の実装がいらない
- **Cons**: 権限が過大。監査ログを書くかどうかが運用者の注意力に依存する
- **Why not**: 監査を「必ず」残す仕組みにならない

## Consequences

### Positive
- 横断してできることが、関数の一覧としてそのまま列挙できる（レビュー・監査の対象が明確）
- 横断操作には必ず監査ログが残る（`__tests__/cross-tenant.test.ts` で実証）
- search_path の乗っ取り（呼び出し側が一時スキーマなどに同名のオブジェクトを置く攻撃）を防げる

### Negative
- 横断処理を追加するたびに、関数・GRANT・テストを書く必要がある
- 関数の中身は RLS に守られないので、関数ごとのレビューが重要になる

### Risks
- **関数の引数で絞り込み条件を受け取り、実質的に汎用関数になってしまう** → 引数は理由や期間など最小限にし、テナント ID を自由に受け取る設計は避ける
- **監査ログの改ざん** → [ADR-0002](0002-separate-db-roles.md) のとおり append-only にし、所有者やスーパーユーザーの UPDATE・DELETE・TRUNCATE もトリガーで拒否する。ただし所有者やスーパーユーザーはトリガー自体を無効化・削除できるので、DB 管理者による改ざんまで検知するには、ログを外部に転送するなどの仕組みが別に必要
